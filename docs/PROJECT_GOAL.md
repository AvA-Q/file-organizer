# 文件整理器：项目目标与验收标准

文档状态：第一版草案  
更新日期：2026-09-30  
文档目的：在任何代码、依赖和 GitHub 配置开始之前，先定义这个项目为什么存在、首版做到什么程度，以及怎样判断首版已经完成。

## 1. 项目名称

推荐名称：`file-organizer`

含义：项目名称用于 GitHub 仓库地址、README 标题和今后的安装说明。

作用：让用户看到名称时就能大致判断项目用途。项目名称优先使用小写英文和连字符，便于在不同系统上使用。

## 2. 一句话定位

这是一个命令行文件整理工具，可以扫描指定目录，并根据文件扩展名安全地分类文件。

含义：一句话定位同时说明产品形态、操作方式和核心结果。

作用：后续新增功能时都要回答一个问题：它是否仍然服务于“安全地分类文件”这个目标。

## 3. 为什么做

常见目录，例如下载目录，会逐渐混入图片、文档、视频和压缩包。手动分类重复、耗时，而且容易误覆盖同名文件。

含义：这里描述的是用户正在经历的问题，不是某个技术方案。

作用：避免因为“想练习 Python”而随意增加与真实问题无关的功能。

## 4. 目标用户

第一版目标用户：主要是我自己，以及需要整理本地目录的普通电脑用户。

含义：目标用户决定术语、操作复杂度和错误提示方式。

作用：第一版不追求企业级批量处理，也不假设用户会阅读复杂配置文档。

## 5. 使用场景

用户下载了一批文件后，希望先查看整理计划，再决定是否执行移动操作。

示例：

```text
Downloads/
├── photo.jpg
├── report.pdf
├── movie.mp4
└── archive.zip
```

期望结果：

```text
Downloads/
├── images/photo.jpg
├── documents/report.pdf
├── videos/movie.mp4
└── archives/archive.zip
```

含义：使用场景说明用户在什么情况下使用，以及输入和输出分别是什么。

作用：它可以直接转化为测试用例和 README 示例。

## 6. 核心目标

接收一个目录路径，根据稳定的分类规则计算文件去向，并在用户确认后执行移动；任何情况下都不能因为同名文件而静默覆盖原文件。

含义：核心目标包含输入、处理、执行条件和最重要的安全约束。

作用：为后续的 `plan_moves()` 和 `apply_moves()` 设计提供依据。

## 7. 第一版必须包含

1. 接收一个待整理目录路径。
2. 根据扩展名识别图片、文档、视频和压缩包。
3. 支持 `--dry-run`，只展示计划，不修改文件。
4. 处理目标目录中的同名文件，不覆盖已有文件。
5. 输出每个移动项的成功或失败结果。
6. 对目录不存在、没有权限和非法参数给出清楚错误。
7. 提供自动化测试，覆盖主要分类规则和安全行为。
8. 提供 README，说明安装、运行、参数、示例和测试方式。

含义：这里只写第一版必须交付的能力。

作用：它是 MVP，也就是最小可用版本。完成这些内容后，项目就可以上传 GitHub，而不必等待所有想法都实现。

## 8. 第一版明确不做

1. 不做图形用户界面。
2. 不做自动定时整理。
3. 不做云端同步或网络上传。
4. 不做人工智能文件分类。
5. 不做撤销上一次整理。
6. 不做跨磁盘事务和复杂冲突合并。
7. 不保证识别没有扩展名或扩展名错误的文件。

含义：非目标不是“这些功能永远不做”，而是“当前版本不为此增加复杂度”。

作用：防止项目范围持续扩大，保持第一个项目可以在较短时间内完成。

## 9. 首版用户流程

1. 用户输入待整理目录。
2. 程序检查目录是否存在并读取文件列表。
3. 程序根据规则生成移动计划。
4. 如果使用 `--dry-run`，程序只打印计划并结束。
5. 如果未使用 `--dry-run`，程序显示计划并要求确认。
6. 用户确认后，程序执行移动并报告结果。

含义：用户流程描述用户看到和经历的顺序，不涉及具体函数实现。

作用：帮助发现缺失步骤，也方便以后增加图形界面。

## 10. 验收标准

满足以下条件时，第一版才算完成：

1. 按 README 的步骤可以成功安装和运行。
2. 图片、文档、视频和压缩包能被正确分类。
3. 无法识别的文件留在原处，或者明确归入 `others`。
4. `--dry-run` 执行前后文件位置完全不变。
5. 目标目录已有同名文件时，不会覆盖原文件。
6. 不存在的目录会返回清楚错误，并产生非零退出状态。
7. 自动化测试全部通过。
8. 执行移动后能够看到成功和失败的统计结果。
9. README 至少包含一个输入输出示例。
10. Git 提交历史中没有虚拟环境、缓存、密码或密钥。

含义：验收标准必须可以被观察和验证。

作用：它把“感觉差不多完成了”变成可以逐项检查的完成条件。

## 11. 技术与安全约束

1. 核心逻辑优先使用 Python 标准库。
2. 先计算移动计划，再执行文件修改。
3. 默认不覆盖任何已有文件。
4. 文件操作必须捕获常见异常，例如权限不足和目标被占用。
5. 核心逻辑不能依赖命令行输出，方便测试和未来复用。

含义：约束是项目必须遵守的工程边界。

作用：减少误删、误覆盖、不可测试和难以扩展的问题。

## 12. 已知风险

1. 同名文件的自动改名规则需要制定清楚。
2. 多个分类可能同时匹配，需要规定优先级。
3. 移动过程中可能遇到权限、文件占用或磁盘空间问题。
4. 扩展名不等于真实文件类型，第一版只按扩展名处理。
5. 用户可能误解“确认后执行”的影响范围，因此预览输出必须清楚。

## 13. 第一阶段的完成定义

本文件的创建和确认代表第一步完成。

第一步完成后，第二步才创建 Python 项目结构、虚拟环境、依赖配置和 Git 仓库。
